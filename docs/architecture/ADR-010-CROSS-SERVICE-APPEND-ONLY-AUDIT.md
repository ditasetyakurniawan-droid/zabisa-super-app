# ADR-010 Cross-Service Append-Only Audit

## Status
Accepted for Phase 3.6.

## Context
Zabisa stores private student data and financial transactions. Sensitive mutations must remain attributable even when the mutation is owned by a bounded context other than Identity.

## Decision
Identity remains the centralized read model for security audit records. Bounded contexts do **not** write directly to `identity_db`.

Sensitive services write an `Audit.Record` event into their own MySQL `outbox_events` table. For audited operations, the business mutation and audit event are committed in the same local database transaction. The existing outbox worker routes `Audit.Record` to Identity's internal audit-ingestion endpoint and routes domain notification events to Notification.

Identity accepts audit ingestion only with `X-Internal-Key`, uses the source outbox event UUID as the audit row primary key, and therefore treats retries idempotently. There are no public/admin update or delete endpoints for `audit_logs`.

Audit records carry:
- actor ID;
- action;
- resource and resource ID;
- minimized before/after state;
- source service;
- IP and user agent where available;
- request ID and trace ID;
- timestamp generated by the audit database.

PII is minimized. Passwords, access tokens, refresh tokens and guardian private payloads are never put in audit events.

## Initial audited mutations
- student create/update;
- guardian relationship request/approve/reject/revoke;
- tahfidz entry create;
- grade create/update/publish;
- report publish;
- donation campaign create/update/lifecycle;
- manual payment verification;
- identity user create and role/status change (existing local Identity audit).

Dynamic permission mutation does not yet exist; the current permission matrix is code-defined RBAC. When permission administration becomes mutable, it must use the same append-only audit contract.

## Failure semantics
Audit delivery is asynchronous but durable. If Identity is temporarily unavailable, the source outbox retains the event and retries with bounded exponential backoff. The source business transaction does not depend on synchronous cross-service HTTP availability.

## Consequences
- no cross-service database queries/writes;
- mutation + audit intent are atomic within the owning service;
- audit delivery is eventually consistent;
- Identity audit ingestion must remain idempotent and internal-only.
